Module 1

The Big Picture

Before diving into code, understand what Microverse does at a high level — and how all the pieces connect.

Microverse is a sandbox AI social simulation game built with Godot 4. Inspired by Stanford's AI Town paper, it places 8 office characters in a virtual workplace where they think, talk, remember, and make decisions entirely on their own — powered by real LLMs.

As the player, you're a god. You watch the simulation unfold, intervene when you want, configure the AI brains, and save the world state whenever you like. Every conversation is real. Every memory persists.

System Architecture at a Glance

project.godot ← entry point, declares autoloaded singletons │ ├── SettingsManager ← global + per-character API settings ├── APIManager ← HTTP calls to LLM APIs ├── DialogManager ← starts/ends conversations (T / L keys) ├── CharacterManager ← tracks which character the player controls ├── MemoryManager ← stores + retrieves character memories └── GameSaveManager ← save / load world state to JSON Office Scene ├── 8 Characters │ └── CharacterController ← movement, pathfinding, animation │ └── AIAgent ← autonomous decision-making │ └── ChatHistory ← per-character conversation log ├── Furniture (chairs, desks) ├── RoomAreas ← named zones characters are aware of ├── CameraController └── GodUI ← god-mode control panel

Key Flows in One Sentence Each

  • ⌨️ Player presses T → DialogManager → DialogService → ConversationManager → LLM API → speech bubble on screen
  • 🤖 AI decision timer fires (every 60s) → AIAgent asks LLM "what should I do?" → moves, sits, or talks
  • 🧠 After every conversation → DialogManager → MemoryManager stores a new memory for each participant
  • 💾 Player presses F1 → GameSaveManager serialises all character states to a JSON file
  • ⚙️ Player changes API provider → SettingsManager persists choice → APIManager picks it up on next call

How Personality Becomes a Prompt

# CharacterPersonality.gd
const PERSONALITY_CONFIG = {
  "Alice": {
    "position": "Frontend Engineer, UI Designer",
    "personality": "Design's thorny rose...",
    "speaking_style": "Opens with '...'...",
    "work_duties":  "UI design, UX...",
    "work_habits":  "Pixel-art stickers..."
  }
}

Plain English

  • This is a GDScript constant dictionary — think of it as a config object that never changes at runtime.
  • Each key is a character name; the value is a nested dictionary of traits.
  • When Alice speaks, the game calls get_personality("Alice") and pastes all 5 fields straight into the LLM prompt — so the AI model literally reads Alice's personality before generating her next line of dialogue.
💡 The insight: characters feel real not because of sophisticated AI, but because the prompt is rich. Personality + memory + current status = deeply contextualised LLM output.

The Decision Loop (Every 60 Seconds)

func make_decision():
  # Skip if already waiting for API
  if character.name in waiting_responses:
    return

  # Different logic if mid-conversation
  if dialog_manager.is_character_in_conversation(
      character):
    await make_conversation_decision()
    return

  # Build a rich context prompt
  var prompt = "You are %s, %s..." % [
    character.name,
    personality["position"]
  ]
  prompt += scene_description
  prompt += status_info
  prompt += task_info
  prompt += "\nChoose: 1=adjust tasks 2=continue"

  # Ask the LLM, parse reply
  var http = await api_manager.generate_dialog(
    prompt, character.name)
  http.request_completed.connect(
    _on_decision_request_completed)

Plain English

  • Guard clauses first — if the AI is waiting for an API reply from last time, skip. No spamming.
  • Different logic mid-conversation — characters can decide what to say next while already talking.
  • Build a prompt — personality + scene description + mood/health/money + task list, all concatenated into one big string.
  • Ask the LLM — the question is simple: "1 or 2?" (adjust tasks vs. continue current task). The AI picks based on full context.
  • Callback on completion — Godot's await pauses the function until the HTTP request finishes, then _on_decision_request_completed handles the response.

What "Autonomous" Actually Means

  • 🏃 Move — AIAgent calls move_to_target() → CharacterController pathfinds to a room or chair using Godot's NavigationAgent2D
  • 💬 Talk — AIAgent calls dialog_manager._try_start_conversation() → full LLM dialogue exchange (see Module 4)
  • 🪑 Sit — AIAgent sends character to a chair; ChairController auto-sits on arrival and adjusts Z-depth for 2D sorting
  • 😴 Idle — just waits for the next decision timer tick
🎯 Why 60 seconds? It's a balance — short enough to feel alive, long enough not to hammer the LLM API with constant requests (which costs money and slows down the game).
Module 4

The Conversation Engine

From pressing T to seeing a speech bubble — a six-step journey through four different classes.

The dialogue system has four layers. Each layer has one job:

1
DialogManager (Singleton)
Listens for the T key. Checks that the selected character is close enough to someone else (< 100 px). Tells DialogService to start a conversation.
2
DialogService
Maintains a dictionary of all active conversations. Prevents the same two characters from having two conversations at once. Creates a ConversationManager for this pair.
3
ConversationManager (RefCounted)
The real engine. Builds the LLM prompt from personality + memory + status + recent history. Calls APIManager. Parses the response. Creates a speech bubble. Saves the exchange to ChatHistory. Then swaps speaker and listener for the reply.
4
APIManager (Singleton)
Creates an HTTPRequest node on-the-fly, sets the right headers for the chosen provider (OpenAI / Ollama / Claude / …), fires the POST, returns the HTTPRequest node to the caller via await.
5
DialogBubble (UI Node)
A NinePatchRect that auto-positions above the character's head. Shows text, follows the character in real time, fades out after 5 seconds.
6
ChatHistory (Per-character Node)
Appends the exchange to an in-memory array keyed by the other character's name. Auto-saves to user://chat_history/Alice_history.json. These are read back on the next conversation as "recent history".

How the Prompt Is Assembled

func build_dialog_prompt(...) -> String:
  var prompt = "You are %s, %s. "
              % [speaker.name, position]
  prompt += "Your personality: %s. " % personality
  prompt += "Speaking style: %s."   % style

  # World context
  prompt += background_prompt      # company + rules
  prompt += company_basic_info     # name, desc
  prompt += company_info           # employee roster

  # Speaker's internal state
  prompt += speaker_status         # mood, health, $$$
  prompt += speaker_memories       # from MemoryManager
  prompt += speaker_tasks          # current task list

  # Listener's public info only
  prompt += "\nYou are talking to %s." % listener.name
  prompt += listener_basic_info    # NO memories exposed

  # Recent history (last 5 lines)
  prompt += chat_history

  return prompt

Plain English

  • Six layers of context stacked in sequence — identity → world → internal state → memories → tasks → the person they're talking to → recent exchanges.
  • Privacy model: the speaker gets their own full memories. The listener's memories are never revealed — just like real conversations where you can't read someone else's mind.
  • Recent history (5 lines) prevents characters from starting every sentence fresh and forgetting what they just said.
  • All of this concatenates into one long string sent as the system prompt to the LLM.

Module 5

The Memory System

Characters remember what happened — and those memories shape everything they say next.

After every conversation ends, DialogManager adds a memory to each participant via MemoryManager. Memories are stored as metadata on each character node, serialised to disk on save.

Five Types of Memory

🧍 PERSONAL
"I prefer working late at night when the office is quiet."
🤝 INTERACTION
"Alice complained about Stephen's Figma comment this morning."
📋 TASK
"Finished the login page redesign. Waiting for Jack's API."
❤️ EMOTION
"Felt frustrated after today's all-hands meeting."
📅 EVENT
"Company announced Q3 performance bonus was cut."

Memory Importance Levels

LOW · 1 pt NORMAL · 3 pts HIGH · 5 pts CRITICAL · 10 pts

When building the prompt, memories are sorted by importance descending, then by recency. Old LOW memories get pruned first when the list grows too long.

Adding a Memory in Code

# MemoryManager.gd
func add_memory(
    character: Node,
    content:   String,
    type:      MemoryType = PERSONAL,
    importance:MemoryImportance = NORMAL
) -> void:

  var memory_obj = {
    "content":    content,
    "timestamp":  time_str,
    "type":       type,
    "importance": importance,
    "created_at": Time.get_unix_time()
  }

  var data = character.get_meta(
    "character_data", {})
  data["memories"].append(memory_obj)
  character.set_meta("character_data", data)

Plain English

  • character.get_meta / set_meta — Godot lets you attach arbitrary data to any node using metadata. Here the entire character state (memories, mood, money…) lives in a dictionary called character_data.
  • One function, four parameters — you only need to specify what you want to remember. Defaults handle everything else.
  • Timestamp is automatic — the current system time is stored so the engine can sort memories by age later.
  • Memories only exist in RAM until GameSaveManager.save_game() writes them to disk.
🔬 Why this matters: Without memory, every conversation starts from scratch and feels hollow. With memory, Alice remembers that Jack ignored a critical bug for two days — and will bring it up the next time they talk, even if it was two play sessions ago.

The API Abstraction Layer

One codebase, nine AI providers. How? A provider registry pattern in APIConfig.gd.

Every LLM has a different API format. OpenAI uses /v1/chat/completions. Ollama runs locally. Gemini needs a Google API key in the URL itself. Claude wants a special anthropic-version header. APIConfig abstracts all of this behind one uniform interface.

The Provider Registry Pattern

# APIConfig.gd — Provider Registry
class APIProvider:
  var url:            String
  var models:         Array[String]
  var requires_key:   bool
  var request_format: String  # openai/gemini/claude
  var response_parser:String

static var _providers: Dictionary = {}

static func _initialize():
  _providers["OpenAI"] = APIProvider.new(
    "OpenAI", "OpenAI",
    "https://api.openai.com/v1/chat/completions",
    ["gpt-4o-mini", "gpt-4o"],
    true,
    {"Authorization": "Bearer {api_key}"},
    "openai", "openai"
  )

Plain English

  • APIProvider is a class that holds all config for one provider — URL, models, whether you need an API key, what request format to use, and how to parse the response.
  • _providers dictionary maps provider names → APIProvider objects. Adding a new provider means adding one entry here.
  • request_format tells build_request_data() which JSON shape to use. "openai" format works for OpenAI, DeepSeek, Doubao, KIMI, and SiliconFlow — they all copied OpenAI's API.
  • static var — data lives on the class, not on instances. Only one copy exists. No need to create an APIConfig object.

Request-Response Lifecycle

1
ConversationManager calls APIManager.generate_dialog(prompt)
Passes the assembled prompt string.
2
APIManager reads SettingsManager for current provider + model + key
Supports per-character override (Alice can use GPT-4o while others use a local Ollama model).
3
APIConfig.build_request_data() formats the body
Wraps the prompt in the correct JSON shape for the chosen provider.
4
APIConfig.build_headers() adds auth headers
Substitutes {api_key} placeholder with the real key.
5
A new HTTPRequest node is created and fires the POST
The node is auto-destroyed after the response arrives.
6
APIConfig.parse_response() extracts the text
Different JSON paths for different providers (e.g., choices[0].message.content for OpenAI, candidates[0].content.parts[0].text for Gemini).
🏗️ Architecture lesson: The Provider Registry Pattern is the same pattern used in real production systems — one central config drives many different back-end implementations without changing the calling code. You've seen this in database drivers, payment processors, and OAuth providers.
Module 7

Save, Settings & Persistence

How the world state survives between play sessions.

Microverse uses a flat-file persistence model: everything is JSON stored in Godot's user data directory (user://). No database, no server.

Files Written to Disk

File Contains
user://saves/{name}.json Full world snapshot: positions, facing direction, sitting state, AI states, tasks, settings
user://settings.cfg Global API type, model, API key, window size, display mode
user://character_ai_settings.cfg Per-character API overrides (Alice → GPT-4o, others → Ollama)
user://chat_history/*.json Each character's conversation log, keyed by the other participant's name
user://custom_social_rules.json Custom rules added through BackgroundStoryManager (office, school, or jail presets)

Settings Signal Chain

When you change the API provider in the settings UI, here's what happens:

GlobalSettingsUI │ user changes provider dropdown ↓ SettingsManager.save_settings() │ writes to user://settings.cfg │ emits settings_changed signal ↓ APIManager ← connected to settings_changed │ reads new api_type + model + key ↓ Next API call ← uses the new provider automatically
📡 Signals are Godot's built-in event system — like JavaScript's addEventListener. SettingsManager broadcasts one signal; every interested system subscribes. No tight coupling.
Module 8

Extending Microverse

Three recipes for making the project your own.

Recipe 1 — Add a New Character

1
Create the scene
Duplicate an existing character scene (e.g. Alice.tscn) in scene/characters/. Name it Zara.tscn.
2
Add the personality config
In script/CharacterPersonality.gd, add a new entry to PERSONALITY_CONFIG with "Zara" as the key. Fill in position, personality, speaking_style, work_duties, and work_habits.
3
Place in the scene
Add Zara.tscn to the Office scene. Add the node to the "character" group so GameSaveManager picks her up automatically. She will immediately have AI decisions, memory, and dialogue.

Recipe 2 — Add a New LLM Provider

1
Add to _providers in APIConfig.gd
Create a new APIProvider.new() entry. Set the URL, available models, whether a key is required, and which request/response format to use ("openai" works for most new providers).
2
Add to the APIType enum
Append your provider name to the enum APIType at the top of APIConfig.gd.
3
Add to GlobalSettingsUI dropdown
Add the provider name to the dropdown items in the settings UI scene. That's it — all routing is data-driven.

Recipe 3 — Change the World (Background Story)

BackgroundStoryManager ships with three presets: Office, School, and Jail. Each preset has 7–8 social rules that are injected into every single prompt. You can add custom rules at runtime: 

# In GodUI or via console
BackgroundStoryManager.add_custom_rule(
  "No one may eat lunch at their desk."
)

# The next conversation prompt will include:
# "Social rule: No one may eat lunch at their desk."

Plain English

  • One function call changes every character's future behaviour because the rule is injected into every LLM prompt from this moment forward.
  • Rules are saved to user://custom_social_rules.json so they persist across sessions.
  • Want to build a Succession scenario? Change the background story to a family company and add rules about inheritance. No code change needed — pure prompt engineering.
